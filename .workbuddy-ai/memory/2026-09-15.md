## Hermes → Blinky integration research & plan

**Ask:** integrate Hermes into Blinky so Blinky reaches feature parity with Hermes.

**Clarified what "Hermes" means:** Hermes Agent by Nous Research
(`github.com/NousResearch/hermes-agent`, docs at hermes-agent.nousresearch.com) —
a self-hosted terminal-native autonomous agent. NOT the Hermes JS engine, not the
Hermes LLM family.

**Key facts gathered (verified against docs, not assumed):**
- License: **MIT** → embeddable/redistributable with attribution.
- Language: **Python 3.11, `uv`-managed**. Same language as Blinky's sidecar.
- **No published wheel or sdist** — cannot `pip install`. Must vendor a git checkout +
  `uv sync`, or run out-of-process. This is the main cost driver for embedding.
- Embedding API: `from run_agent import AIAgent`; params include `quiet_mode`,
  `enabled_toolsets` / `disabled_toolsets`, `skip_context_files`, `skip_memory`,
  `max_iterations`, `ephemeral_system_prompt`, `base_url`, `platform`.
- External driving: ACP, TUI-gateway JSON-RPC, OpenAI-compatible HTTP API.
- Computer use: `computer_use` toolset → **`cua-driver`** over MCP stdio (trycua/cua).
  Background control, no cursor movement, no focus steal. UIA (Win) / AX (mac) / AT-SPI (Linux).
- ~90 bundled + ~60 optional skills, `SKILL.md` / agentskills.io-compatible.
- Gateway supports 21+ messaging platforms.

**Blinky state assessed from the tree (deeper than README suggests):**
- Already has: `computer_use/` (tools.py 2479 L, loop.py 931 L, step_planner, vision_planner,
  text_grounder, recipes, recovery, metrics), `tools/registry.json` + `utils/generalizer.py`
  + `utils/sufficiency_checker.py` (a primitive learning loop), `.agents/skills` +
  `skills-lock.json` (1 skill: caveman), an MCP **server** (`aicut/aicut_mcp.py`),
  an MCP **client** shim pattern (`computer_use/linux_mcp.py` → `backend.linux_mcp_compat`),
  WhatsApp backend (whatsapp-web.js), WS server on 9001, wake word (`hey_blinky.onnx`).
- Missing vs Hermes: persistent memory, cron/scheduler, subagents, multi-surface gateway,
  approval/capability-manifest guardrails.
- Ahead of Hermes: OCR + UIA `@ref` map + `ui_map_cache`, transparent overlay, Sarvam voice.

**Recommendation delivered:** Route A (embed `AIAgent`) for the brain, but do the three
Hermes-independent transplants first. Order: Phase 0 boundary → Phase 1 cua-driver actuator
(highest value, independent) → Phase 2 MCP tool bus → Phase 4 file contracts (cheap) →
Phase 3 Hermes brain → Phase 6 guardrails → Phase 5 cron/surfaces.
Fallback if `uv` ↔ `.venv` reconciliation fights back: Route B (drive out-of-process via JSON-RPC).

**Critical gotcha identified:** Tauri talks to the Python sidecar over JSON on **stdout**
(`main.py` does `print(json.dumps(...), flush=True)`). `AIAgent` defaults to
`quiet_mode=False` and prints spinners → **must set `quiet_mode=True`** or the wire
protocol corrupts. Same applies to any `uv` banner output.

**Deliverable:** `docs/HERMES-INTEGRATION-PLAN.md` — parity matrix, three routes with
tradeoffs, phased plan mapped to real file paths, gotchas, open questions.

**Not yet done / next:** Phase 1 spike — verify `cua-driver` works standalone over MCP
outside Hermes. Then swap the actuator behind the existing `linux_mcp_compat` signatures so
`tools.py` / `loop.py` need zero changes.

## Phase 1b — Rust cua bridge + the "second cursor" and "click didn't land" bugs

Sahil ran `bun run dev`, asked Blinky to click Instagram, and reported: the AI cursor glided
there but **Instagram didn't open**, and a **second ("hermes") cursor appeared**. Both
diagnosed and fixed.

### Root causes

1. **Second cursor.** `set_agent_cursor_enabled` **requires** `session`
   (`"required": ["session","enabled"]`). The first cut called it with `{"enabled": false}`,
   so it failed validation and the driver's `Cua.AgentCursorOverlay` was never hidden. On top
   of that, omitting `session` makes the driver mint an **implicit session per CLI call** —
   so the overlay and the element-snapshot cache were never shared.

2. **"Click didn't land" — the big one.** Desktop-scope clicks are **not** background:

   ```console
   $ cua-driver call click '{"scope":"desktop","x":237,"y":1422,"delivery_mode":"background"}'
   { "delivery": { "mode": "not_applicable" }, "effect": "unverifiable", "route": "global_input" }
   $ cua-driver call get_cursor_position '{}'
   { "x": 237, "y": 1422 }
   ```

   `delivery_mode` is ignored in desktop scope — the driver injects global input, so the real
   pointer moves. Only **window scope + `element_index`** is genuinely background
   (`route: "synthetic_events"`).

### Hypotheses killed (don't re-investigate)

- **The overlay does not swallow clicks.** Both `Cua.AgentCursorOverlay` windows are 2560×1600
  and always-on-top, but `GetWindowLongPtr(GWL_EXSTYLE)` = `0x80800A0`:
  `WS_EX_TRANSPARENT | LAYERED | NOACTIVATE | TOOLWINDOW` → click-through.
- **The coordinate pipeline is correct.** `capture_screen()` grabs 2560×1600, then
  `thumbnail((1920,1080))` → 1728×1080, `sx = 0.675`. UIA bounds (screen-absolute) are scaled
  **down** to screenshot space in `main.py`; the frontend `getPhysicalClickablePoint()` scales
  back **up** by `screen_width / width` = 1.4815. Round trip is identity, confirmed live.
- The user's own screenshot + log show the locator was **right**: it matched the **Instagram
  bookmark** in Edge's bookmarks bar
  (`Locator accepted local match 'instagram' to 'Instagram' score=1.290 candidate_count=1`).

## Phase 1b follow-up — the fallback is now background too

The first cut still dropped to a **desktop-scope** click when no element matched, and desktop
scope moves the real cursor. That defeats "background cursor as the ai cursor" for exactly the
targets that need the fallback (browser bookmarks, canvas, video). Replaced it with a
**window-scope pixel click**, which stays inside the target window.

### Measured

```console
window_bounds   = {x: 0, y: 0, width: 2560, height: 1528}   # "Hermes"
screenshot      = 1567 x 935                                 # factor 0.6121
$ cua-driver call click '{"scope":"window","pid":17040,"window_id":396034,
                          "x":784,"y":918,"delivery_mode":"background"}'
{ "delivery": {"mode":"background"}, "effect":"unverifiable", "route":"synthetic_events" }
```

Window-scope `x, y` are **downscaled window-screenshot** pixels (the `max_image_dimension`
ceiling, 1568), **not** window-local physical pixels. So:

```
local = (screen - window_bounds.origin) * (screenshot_size / window_bounds.size)
```

and the dimensions only come back when `include_screenshot: true` — hence the fallback
re-snapshots with a screenshot written to a scratch file (`%TEMP%\blinky-cua-window.png`) so the
response stays small. Passing physical pixels would land every fallback click ~1.6× too far
down and right.

**Cursor check:** the real pointer did not move across two window-scope clicks (it only moved
because the user was moving the mouse — it ended at 1381,865, neither click point).

### Final `click_element_at` ladder

1. `list_windows` → frontmost real window covering `(x, y)`.
2. `get_window_state(include_screenshot=false)` → rank invokable **labelled** elements
   (exactness → shortest label → interactive role) → `click` by `element_index` + `snapshot_id`.
3. Else re-snapshot **with** the screenshot → window-scope pixel `click`.
4. Else `click_element_impl` drops to the desktop `SendInput` point click (last resort only).

### Stale overlays (driver-side, not ours)

A **third** `Cua.AgentCursorOverlay` appeared during testing (pid 19656, plus 28780 and daemon
41304). Thin `cua-driver.exe` clients don't always exit and each owns a fullscreen overlay. They
are click-through (`WS_EX_TRANSPARENT`) so they don't block input, but they are the phantom
cursor if a session leaves its cursor enabled. Blinky's `blinky` session reports
`cursor_visible: false` / `enabled: false`. `cua-driver stop` clears strays.

### Verification

- `cargo check` clean after every change; `bun run typecheck` clean.
- Notepad end-to-end test **failed to run**: `launch_app` needs `name`/`aumid` (not `app`), and
  the Store Notepad (`Microsoft.WindowsNotepad_8wekyb3d8bbwe!App`) launches `active: False`
  (confirming no focus steal) but **never materialises a window** — the pid had no window at all
  after 9s. Use a non-packaged target (e.g. `notepad.exe` via `path`, or an already-open window)
  for the next attempt.

## Phase 1b follow-up — the lag was the transport, and every click was hitting our own overlay

User report: *"it clicks instagram but when the ai cursor reaches there it is so much lag it in not
instant there"*, plus the log line
`blinky: cua element click failed (get_window_state: unparseable driver output); falling back to point click`.

### Root cause 1 — `cua-driver call` costs ~1.45s of pure process startup, per call

Measured the driver directly. The floor is fixed process cost, not daemon work —
`get_cursor_position` returning **28 bytes** took **1.45s**:

| call | `cua-driver call` (spawn per call) | `cua-driver mcp` (one persistent child) |
| --- | --- | --- |
| `get_cursor_position` | 1.45 s | 0.006 s |
| `list_windows` | 1.80 s | 0.08–0.17 s |
| `get_window_state` tree | 2.40 s | 0.15 s |
| `get_window_state` +screenshot | 2.40 s | 0.39 s |
| `click` | ~1.80 s | 0.09 s |

The ladder (list windows → walk tree → click) was therefore **~8 seconds**. That was the "lag".

**Fix:** `windows/src-tauri/src/platform/cua.rs` now keeps one long-lived `cua-driver mcp` child
(JSON-RPC over stdio) behind a `Mutex`, with a reader thread + condvar keyed on JSON-RPC id.
Ladder is now **~0.4s**. The old `last_json_object()` brace-scanner is gone entirely — the
`unparseable driver output` was never a parsing bug, it was the child **blocking on a full stdout
pipe** because the old poll loop never drained it. Both pipes are now drained continuously.

`cua-driver mcp` exits with code 0 on stdin EOF, so Blinky closing reaps it — no teardown needed.

### Root cause 2 — `window_at()` was resolving to Blinky's own overlay

`Blinky Highlight Overlay` is fullscreen, always-on-top, transparent — and sits at **`z_index` 18,
above Edge at 15**. It was missing from `NON_TARGET_TITLES`, and it sorted first, so **every** click
resolved to Blinky's own overlay and went nowhere.

**Fix:** exclude Blinky's own windows **by pid** (`std::process::id()`, exact) plus the title list
(backstop), and sort frontmost-first on `z_index` instead of trusting the driver's undocumented list
order. Also added `on_screen_only: true` to `list_windows`, which drops the phantom minimized
windows (see below).

### Root cause 3 — ~1.2s of deliberate frontend delay

`autopilot.ts` awaited `setTimeout(..., 620)` after emitting the cursor move, and `Overlay.tsx`
then ran a **600ms** glide whose `onfinish` triggered the ripple. The glide is a GPU-composited CSS
animation in a separate overlay window, so it never needed to gate the action.
**Fix:** artificial wait removed; glide 600ms → 220ms.

### The `(710,1890)` mystery — resolved, and the coordinate formula is confirmed

A `click` at window-scope `(700,400)` reported *"Posted click to Chromium pid 37932 at
(710,1890)"*, which no scale explained and briefly made `window_local()` look wrong. The real cause
had nothing to do with coordinates: **pid 37932 owned two windows**, and the driver auto-resolved to
a phantom `219x30@9,1489` one. `9+700=709`, `1489+400=1889` — matching within 1px.

So **`window_local()` is correct**; the window was wrong. Blinky always passes an explicit
`window_id`, so it cannot recur here — but it is a trap for anyone who omits `window_id`.

Also corrected: the screenshot scale is **not** the constant 0.6121 recorded earlier. The same
2560×1528 window reported `1567x935` (0.6121) in one session and `1456x869` (0.56875) in another.
Read it from the response every call; never cache it.

### New driver facts

- **Refusals are successful tool calls**: `{"refusal": {"code", "message"}, "status": "refused"}`,
  often with `isError` unset. Trusting `isError` alone reads a refused click as done and suppresses
  the fallback. Must be checked explicitly.
- **A bare `element_index` is always rejected** (`snapshot_id_required`). It must travel with
  `snapshot_id`, or be replaced by `element_token` (opaque, e.g. `s00000001:0`, carries the window +
  snapshot). `element_token` is now preferred.
- **`get_window_state` error shape**: `isError: true`, `structuredContent` = `{code}`, and the
  human reason in `content[].text` — read the text block, not the code.
- **UWP apps expose no element tree.** Windows Settings (`ApplicationFrameHost`) returned
  **0 elements**; UWP content lives in a child process. Those apps always take the pixel rung.
  Chromium is fine (Edge: 324 elements, 42 invokable+labelled).
- **`scroll`/`type_text`/`press_key` all take `pid`/`window_id`** for genuine background delivery.
  Desktop scope is *not* background for them either. `scroll` now resolves the window under the
  point and stays window-scoped, so it no longer drags the real cursor.
- **A typed `browser_*` family exists** (`browser_prepare`/`browser_click`/`browser_type`/
  `browser_pointer`/`get_browser_state`) driving Chromium over CDP — background *and* reliable, with
  `browser_click` taking viewport CSS px or a page `ref`. **Gated**: `browser_prepare` refuses
  without an explicit launch grant (`--grant existing-profile`). Phase 2 work, not a dependency now.

### Verification

- `cargo check` clean; `bun run typecheck` clean.
- Dry-run mirror of the new ladder (`tmp/diag/verify_ladder.py`) confirmed the overlay (z=18) and
  all four stale `Cua.AgentCursorOverlay` windows (z=16..13) are excluded, and that a screen point
  now resolves to a real app window.
- **Still open:** a live end-to-end `bun run dev` + "click instagram" run. Note the `click` response
  carries `effect: "unverifiable"` on Chromium — the driver posts the event but cannot confirm
  Chromium acted on it, so if Instagram does not open the next step is the `browser_*`/CDP rung.

## Phase 1b follow-up 2 — the freeze, and the screenshot call nobody needed

User report: *"cursor glide is ok just the clicking is very lagging and sometime the blinky window
get non responsive also when u added that cua driver thing"*.

### Root cause — synchronous Tauri commands run on the UI thread

The actuator commands (`click_element`, `click_screen_point`, `scroll_at_point`, `type_text`) were
plain `#[tauri::command] fn`. Confirmed from the tauri-macros source
(`tauri-macros-2.6.1/src/command/wrapper.rs`): a sync command's generated wrapper is

```rust
let result = $path(#(match #args #match_body),*);
let kind = (&result).blocking_kind();
kind.block( #resolver );
```

— **no spawn, no thread hop**. It runs on the thread that dispatched the IPC message, which on
Windows is the UI thread. The cua bridge blocks there: pipe write, then a condvar wait with a
multi-second ceiling (and a session handshake on the first call). Result: laggy clicks *and* a
non-responsive window. It was invisible before because the old body was pure `SendInput` —
sub-millisecond.

**Fix:** added `actuator()` in `common/src-tauri/src/lib.rs` wrapping
`tauri::async_runtime::spawn_blocking`, and made all four commands `async fn`. (`run_tutor` /
`run_agent_query` were already async, so the Python path was never implicated.)

### Second win — `max_image_dimension` makes the screenshot call unnecessary

`get_config` reports a **persistent** `max_image_dimension` (1456). The window screenshot is the
window scaled by `scale = min(1, cap / max(width, height))`. Verified exact against real
screenshots on every capped window, and a corner point computed both ways agreed to **0 px**.

So the pixel fallback no longer calls `get_window_state` for the dimensions. That call cost
**0.4–0.9s** (it grabs, encodes and writes a PNG) and we only ever wanted two integers from it.

Measured stage costs over the persistent transport:

| call | cost |
| --- | --- |
| `list_windows` (`on_screen_only: true`) | 0.10–0.14 s |
| `get_window_state` tree only | 0.10–0.19 s |
| `get_window_state` capture-only | **0.4–0.9 s** |
| `click` | 0.09 s |

Ladder now **~0.35s in both branches**; the pixel branch used to be ~0.8–1.1s. This also explains
"very lagging": UWP apps (Settings) return **0 elements**, so they always took the pixel branch
and always paid the screenshot.

### Corrections to earlier notes

- The screenshot factor is **not** session-dependent noise. It changed 0.6121 → 0.56875 because
  `max_image_dimension` changed (1568 → 1456). It is fully derivable from `get_config`; the
  earlier "never cache it" advice was wrong.
- `screenshot_h` is derived from `shot_w`, not from `h` directly: a 2560×1528 window at cap 1568
  reports **935**, while scaling h directly gives 936.
- Small *windowed* (non-maximized) windows differ by ~2px from the derived value — that is the
  DWM extended-frame vs `GetWindowRect` difference, ~2px in screen space. Irrelevant for clicking.

### Instrumentation added

`cua.rs` now logs, without needing a debug flag:
- `blinky: cua-driver transport started in <dur>` — once per healthy run; repeats mean the child
  is dying and every action is paying a fresh spawn + handshake.
- `blinky: cua click slow: <total> via <rung> on pid <pid> (windows <dur>, tree <dur>) -> <outcome>`
  — only when a click exceeds 400ms, naming the stage that ate the time.

## Phase 1b follow-up 3 — "in Settings it always clicks something else"

User: *"when in settings window app it always click accounts no matter what / even though the cursor goes in
the right position / it clicks something else after the edition of cua driver"*.

Two independent defects, both confirmed by measurement. Together they explain the report exactly, because
the AI cursor and the click are computed from **different signals**.

### Defect A — `window_at` trusted `bounds` + `z_index`, and bounds are not visibility

`window_at(x, y)` took the frontmost window whose *bounds* contain the point. Bounds containment is a proxy
for "this window is visible here", and it collapses the moment maximised windows overlap.

Measured (`tmp/diag/probe_window_at.py`), with Settings open and the editor maximised above it:

```
kept, frontmost first
  z=9  pid=9072  Blinky - Antigravity IDE  (0,0,2560,1528)  CONTAINS <-- WINNER
  z=8  pid=8956  Settings                  (0,0,2560,1528)  CONTAINS
```

Every point inside Settings resolved to the **editor**, so clicks meant for Settings were dispatched into the
editor with the editor's pid and editor-local coordinates. The driver's `z_index` was *honest* — the OS
z-order agreed the editor was above (`probe_zorder.py`: IDE rank 4, Settings rank 5). The mistake was the
proxy, not the ranking.

**Fix.** `window_at` now resolves in three rungs:
1. **OS hit-test** — `WindowFromPoint` → `GetAncestor(GA_ROOT)`, joined onto the driver's window list by
   `window_id`. The driver's `window_id` **is the Win32 HWND** (verified: Settings 1051900, Edge 1312662,
   IDE 2689014 all agree in both views), so the join is exact. The hit-test also **skips layered/transparent
   windows for free**, so Blinky's fullscreen overlay no longer needs to be reasoned about.
2. **`GetForegroundWindow`**, if it covers the point.
3. The old `z_index` scan, kept so nothing regresses.

### Defect B — the cursor used the point, the click used the text

`pick_element` ranked label matches by `(exactness, name.len(), role_rank)` — **the click point was discarded
whenever a label was supplied**, and the frontend always supplies one. So the AI cursor glided to the point
the planner aimed at while a completely different control was invoked. That is precisely "the cursor goes in
the right position … it clicks something else".

Worse, `frame_distance` — the only proximity signal, used solely when there was *no* label — was comparing
**incompatible spaces**: `x - target.x` is a *physical* window-local pixel, while `frame.x/w/h` are in the
driver's **downscaled screenshot space** (0.56875× for a 2560-wide window). Every distance was wrong, and
wrong directionally: frames near the top-left always looked closer, which is exactly where a sidebar lives.

**Fix.** `frame_distance` converts the point with `window_local` first, and returns `0` when the point is
*inside* the frame. `pick_element` now ranks `(exactness, distance, length, role)` — proximity breaks ties,
exactness still outranks proximity so a precise match is never displaced by a looser-but-closer one.

### Windows Settings cannot be clicked in the background at all

Separate from the above, and worth stating plainly because it bounds what Phase 1b can promise:

- `get_window_state` on Settings **sometimes** returns 0 elements: `degraded: true`,
  `degraded_reason: "ax_tree_empty"`, `escalation.recommended: "px"`. Another Settings instance
  (`applicationframehost.exe`) returned **79 elements on the first call**, and a freshly launched one
  returned 79 immediately — so the element rung *is* viable, and the driver's own advice is to re-snapshot.
  `window_tree()` now re-snapshots once after a 150 ms settle and logs the degraded reason.
- Window-scope **pixel** clicks on Settings fail outright: `tool_invocation_failed`, with the contradictory
  human message `"The operation completed successfully. (0x00000000)"`. This is **not** a units problem —
  downscaled px, physical px, and an out-of-bounds point all fail identically (`probe_px_units.py`).
- The pattern: a UWP **`ApplicationFrameWindow`** accepts window-scope synthetic clicks; a bare
  **`Windows.UI.Core.CoreWindow`** refuses them. Modern Windows 11 Settings is a bare CoreWindow, so with no
  tree and no frame there is **no background path** — Blinky falls through to desktop scope
  (`route: global_input`), which works but moves the real cursor.

### Tooling notes

- The driver puts the **machine code** in `structuredContent` and the **human reason** in `content[].text`.
  Reading only the structured side is why `tool_invocation_failed` stayed opaque; `probe_tools.py` now
  returns both.
- `element_token` is invalidated by **any** subsequent `get_window_state` on that window (`s00000001` →
  `s00000002`), and a stale one is refused with `stale_element_token`. A probe that fetched the tree twice
  before clicking was silently testing nothing.
- Element field names: the label lives in **`label`** (not `name`), and `frame` uses **`x/y/w/h`** (no
  `width`/`height`). `frame` is present on 74/85 elements and does *not* require `include_screenshot`.
- `bring_to_front` is refused (`foreground_unavailable`) when Windows declines the activation, and the
  window-scope `foreground` delivery mode fails the same way.

## The Settings misclick, actually solved — `window_local` was scaling by 1/0.56875

The "it always clicks accounts no matter what / the cursor goes to the right position but it clicks something
else" bug is fixed, and the root cause was **not** window resolution. Two defects, both in the click path.

### 1. Window-scope coordinates are PHYSICAL, not downscaled (the big one)

`window_local()` scaled screen points by `min(1, max_image_dimension / max(width, height))` — 0.56875 for a
2560-wide window — before sending them as window-scope `x, y`. That is wrong. The driver's **prose** says
window-scope `x, y` is "window-local screenshot pixels", but its **data** says physical:

```
Settings window 2560x1528, cap 1456, reported screenshot 1456x869
frame extents: max_right=2560  max_bottom=1528      <- the window's own size
frame of role=Window: {x:0, y:0, w:2560, h:1528}    <- literally the whole window
```

Frames cannot live in a 1456-wide space if they reach 2560. Decided it by clicking the same element
expressed both ways:

| trial | route | page delta | real cursor |
| --- | --- | --- | --- |
| window scope @ **physical** (1505,557) | `accessibility` | **+11 -14** | unmoved |
| window scope @ screenshot (855,316) | `synthetic_events` | 0 0 | unmoved |
| desktop scope @ screen (1505,557) | `global_input` | 0 0 | **MOVED** |

Only physical acted, and it acted without moving the pointer. So the scaling put every window-scope click
**1.758x too close to the window's top-left**:

```
nav "System" physical centre (234,302) -> scaled (133,172)
account card physical x 9..443, y 74..187   <- (133,172) lands INSIDE it
```

The AI cursor is drawn at the true screen point; the click was delivered at the scaled one. On Settings'
left nav — all in the sidebar — that is the account card. **That is the reported bug, arithmetically.**

Fix: `window_local` is now `(x - target.x, y - target.y)`. `window_local_reported` and `scratch_screenshot`
deleted (dead), and `max_image_dimension()` deleted with them — it existed *only* to serve this conversion,
so the click path also lost a blocking `get_config` round trip.

**Correction to my own earlier note:** `frame_distance`'s original `x - target.x` form was already correct
(physical vs physical). My earlier "units fix" wrapping it in `window_local()` *introduced* the mismatch it
claimed to fix. `frame_distance` is back to physical, and the doc section claiming a units bug is rewritten.

### 2. Settings nav items expose `select`, not `invoke`

`pick_element` required an `invoke` action, so it rejected every Settings nav item — they advertise only
`select`:

```
Home               ListItem  select  {x:25, y:215, w:419, h:54}
System             ListItem  select  {x:25, y:275, w:419, h:54}
Network & internet ListItem  select  {x:25, y:396, w:419, h:54}
```

So every nav label ranked to `None` and every nav click fell through to the pixel rung — the rung with the
coordinate bug. The two defects stacked.

The driver drives a `select`-able element by token perfectly well. Measured three for three, each verified by
the destination page's own vocabulary in the new tree, cursor unmoved:

```
'Network & internet'  -> +44 -13   Wi-Fi, Ethernet, VPN, Proxy, Airplane mode
'Bluetooth & devices' -> +49 -39   Bluetooth, Mouse, Keyboard, Cameras
'Personalization'     -> +45 -49   Background, Colors, Themes, Lock screen, Taskbar
```

Fix: `is_invokable` -> `is_actionable`, backed by `ACTIVATING_ACTIONS` = invoke, select, toggle, expand,
collapse, check, uncheck, press, click, open. Excluded on purpose: `focus`, `scroll_into_view`, `set_value` —
not activations, and accepting them would let `pick_element` report success while doing nothing.

### 3. `cua::click` was still desktop scope

`click` dispatched `scope: "desktop"` (global input injection, moves the real pointer) while `scroll` had
already been moved to window scope — an inconsistency that was the "spawned a new cursor" complaint. Now it
resolves `window_at` and uses `click_window_point`, with desktop scope only as a last resort when no window
resolves.

Caveat, logged not escalated: window-scope pixel clicks are **inert on XAML** (`route: synthetic_events`;
measured — a nav-item pixel click reported success and changed nothing). `accessibility` works, `synthetic_events`
does not. Deliberately not auto-escalated to desktop scope: that moves the cursor and would double-act on Win32
apps where synthetic events do work. `warn_inert_pixel_click` logs it instead.

### 4. What the hit-test actually bought (less than I claimed)

Replayed the old rule faithfully (same `NON_TARGET_TITLES` filter, highest `z_index` among containing windows)
against the hit-test over six points: **agree=6, disagree=0**. The driver's `z_index` is a faithful stacking
order (matches `EnumWindows` top-to-bottom exactly). So the hit-test is robustness, not a proven causal fix —
keep it, but it is not what made Settings work.

Also: the earlier `probe_new_ladder.py` "failure" was a mis-designed test. With the IDE maximised over
Settings, `points hit-testing to Settings: 0` is the *correct* answer. A test point that belongs to another
window proves nothing.

`ApplicationFrameHost.exe` (pid 15388) -> **84 elements**, element rung fully works, background.
`SystemSettings.exe` (pid 656) -> **0 elements** (`ax_tree_empty`), no element rung. The old note saying

## Sidecar process shapes (for reference)

Two shapes, and the difference matters:
- `common/python/main.py` — **one process per question**. `run_python_worker` spawns it, writes a
  single JSON payload to stdin, reads JSON events line-by-line from stdout, and the process exits.
  This is why the frontend autopilot's clicks go through the Rust bridge instead: a Python click
  would pay an interpreter startup per click.
- `python/wake_word.py` — **long-lived**, spawned once at startup with piped stdin so Rust can send
  pause/resume (the `[WakeWord] Paused via stdin` lines). `whatsapp_backend/server.js` is likewise
  long-lived, but Node.
- Wiring: stdin piped, **stdout piped and is the protocol**, stderr inherited (logs go there).
  `python_executable()` discovers `python_runtime/Python313` or walks up for `.venv`.
- **Not** Tauri's official sidecar — there is no `externalBin` in `tauri.conf.json`; the script is
  spawned with a discovered interpreter.
